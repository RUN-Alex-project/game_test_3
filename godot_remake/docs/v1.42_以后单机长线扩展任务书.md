## 0. 使用规则

### 0.1 一次只下发一个版本

开发工程师一次只能接收当前已签署版本后的一个版本任务。一个版本完成后，必须提交代码、数据、测试、证据和交付报告；在 PM/SE 独立复验并正式签署前，禁止开始下一个版本的生产改动。

允许的提前工作仅限于不改生产代码、不改数据、不改场景、不改存档、不改发布包的资料反查。提前反查结论必须标为待验收，不能被写入玩家可见功能或发布说明。

### 0.2 DeepSeek V4 Flash 纯文本执行规则

本任务书的正式开发与大体量执行者是 DeepSeek V4 Flash。它的任务输入只允许可复制文本、源代码、JSON、TSV、资源路径、节点属性、测试命令和日志；任何非文本附件均不属于开发输入。

凡是执行量大的工作，必须由该开发执行者完成。包括但不限于：

1. 对 E:\魔域 中 2.2、2.3、2.4 的批量文本、脚本、地图、任务、物品和角色反查。
2. 大量地图、任务、固定冒险者、物品、台词、证据 token 的录入与校验。
3. 大规模存档迁移矩阵、长周期模拟、批量负向测试、发布构建、哈希和文档一致性检查。
4. 大批量资源导出、清单核对与资产来源登记。

Codex/PM/SE 的职责仅限：产品策划、版本范围、架构决策、任务拆分、证据审查、关键抽样复验、风险判断与签署。Codex 不亲自承担大体量实现、批量迁移、全量反查或重复性测试执行。

每个开发交付报告必须列出：

1. DeepSeek V4 Flash 实际执行的批量工作。
2. 输入、输出和非视觉约束。
3. 主开发如何复核批量输出。
4. 哪些结论仍是 evidence_gap。

### 0.3 结构化验收规则

开发与自动化验收必须使用：

1. 节点树、资源路径、角色 ID、坐标、尺寸、global_rect、z_index。
2. 按钮 pressed、真实输入事件、对话 action、地图入口、公开 service API。
3. 持久状态差、operation_id、账本、日志和自动化断言。
4. 本地版本文本/脚本 token 的精确命中。

## 2. 本地版本借鉴与原创扩展边界

### 2.1 内容分类

后续所有内容注册表都必须使用下列分类之一：

| 分类 | 定义 |
|---|---|
| local_version_confirmed | 可由本地 SWF 文本、脚本或资源 token 支持 |
| local_version_partial | 仅确认名称或局部行为，完整规则未确认 |
| singleplayer_extension | 本项目原创单机设计，例如拍卖会、NPC 日结经济、异步排行榜 |
| evidence_gap | 合理但没有本地证据；不可称原版还原 |

### 2.2 已知可借鉴方向

本地 2.3/2.4 已经确认可用于借鉴的方向包括：

1. 主线、支线、挑战和日常任务目录。
2. 固定朋友、送礼、邮件、好友委托和关系阶段。
3. 资源、声望、产业、城堡、设施升级。
4. 战斗力排行榜入口与分段挑战。
5. 二代幻兽、幻兽炼狱、兽王、元素装备、玄铁、陨铁、宝石融合。
6. 树心、港口、南城、边关、冰封、黑渊等地图名称与战役路线。

### 2.3 不得夸大的结论

1. 未完成稳定导出的 2.2 不能作为具体机制证据。
2. 地图名字不代表完整地图拓扑、角色坐标或全部交互已确认。
3. 本地版本存在朋友、资源和排行榜入口，不代表其存在完整拍卖行或联网玩家经济。
4. 单机固定冒险者、异步 PvP、拍卖会必须标为 singleplayer_extension。

### 2.4 仓库边界

1. 不提交原始 SWF、全量 FFDec 导出目录、JRE、临时 p-code、系统临时文件或无用途日志。
2. 若需导入最小资产，必须登记来源版本、角色号/文本 token、用途、哈希和许可证风险。
3. 新二进制资产必须经 PM/SE 审查必要性，不能因为可能以后用而整包导入。

### 3.1 四条并行循环

| 循环 | 玩家目标 | 主要回报 |

4. 主线不要求参与拍卖、擂台或高关系内容；这些是增强体验，不是强制门票。

## 4. 全局数据、存档、事务与 UI 合同

### 4.1 v22 扩展状态命名空间

从 v1.43 起，新长期状态统一放入 GameState.expansion_state；禁止把每个新系统零散地加到 GameState 顶层。

初始数据合同如下，字段应随版本逐步启用：

~~~json
{
  "revision": 1,
  "world_seed": 0,
  "day_sequence": 0,
  "adventurers": {},
  "relationships": {},
  "mailbox": [],
  "commission_state": {},
  "rankings": {},
  "season": {},
  "economy": {},
  "properties": {},
  "auction": {},
  "campaign": {},
  "collections": {}
}
~~~

旧档迁移必须从固定 schema 默认值构建 DTO，不能读取当前运行中的 GameState 值。加载成功后一次性提交 DTO；失败时内存必须不变。

### 4.2 幂等与原子服务

以下操作只能由服务层执行，UI 不得直接改背包、金币、魔石或持久化字典：

1. 送礼、邮件、委托领取和奖励发放。
2. NPC 直接交易。
3. 拍卖上架、出价、流拍、成交和退款。
4. 日结、周结、赛季结算。
5. 产业产出、设施升级、领地奖励。
6. 图鉴、称号和任务奖励。

每个动作必须有 operation_id，或有可由稳定输入推导的幂等键。重复点击、回调重放、读档、跨日和事件重入都不得造成重复扣物、重复加关系或重复发奖。

### 4.3 确定性日结

NPC 日程、日常池、竞价和世界事件的随机输入统一为：

~~~text
world_seed + game_day + system_id + entity_id + event_sequence
~~~

关键奖励不得使用不可保存、不可复现的随机状态。

### 4.4 UI 通用验收

1. 新面板必须启动隐藏、具备明确关闭方式和返回行为。
2. 不得遮挡现有 HUD、底栏或状态提示；以 global_rect 和 z_index 验收。
3. 长列表使用分页或滚动；长文本有裁剪、换行或滚动策略。
4. 锁定入口仍可点击并显示具体原因，不能静默 disabled。
5. UI 自动化必须走按钮 pressed、真实对话 action、真实地图入口或正式 service API。

### 4.5 测试通用验收

每个版本至少新增：

1. 数据 schema 或注册表测试。
2. 核心服务状态机测试。
3. 真实 UI 或主场景集成测试。
4. 六项以上真实变异负向测试；先断言变异生效，再由正向同一验证器命中精确错误码。
5. 新增存档字段的迁移、缺字段、坏档、加载失败内存不变测试。
6. 相邻回归、全量 runner 和主场景冒烟。

严禁：

1. 只查函数/字符串/token 存在。
2. 直接写入本应由生产流程完成的终态后声称验证流程。
3. 用测试 helper 替代生产 dispatcher。
4. 仅断言错误列表非空。
5. 以非结构化主观判断替代节点属性、运行时状态和自动化验证。

### v1.43：固定冒险者 I——名册、关系与好友委托

#### 目标

引入 12 名本地固定冒险者，完成可保存、可审计的关系与好友委托系统。此版本是 v22 存档迁移版本。

#### 数据与存档

1. 从 v21 迁移到 v22。
2. 启用 expansion_state.revision、world_seed、adventurers、relationships、commission_state。
3. 新增 data/adventurers.json、data/adventurer_commissions.json、data/relationship_rules.json。
4. 12 名角色必须有稳定 ID、关系阈值、偏好物、初始背包摘要、初始幻兽摘要、对话入口和剧情定位。

#### 玩家功能

1. 卡萨诺城新增“冒险者公告板”入口；不得在主城地图塞入 12 个新演员。
2. 名册显示：名字、定位、关系阶段、最近动态、可用委托、送礼状态。
3. 首批委托必须覆盖：收集材料、击败指定怪、探索地图、交付物品、幻兽培养、协助战役。
4. 送礼只能通过真实背包物品，不允许按钮直接增加关系。
5. 关系阶段为认识、朋友、知己、恋人、爱人。恋爱只作为可选文本关系，绝不影响主线或造成失败结局。
6. 关系历史显示来源、游戏日、对象、数值变化、原因。

#### 服务边界

新增 AdventurerService、RelationshipService、CommissionService。面板只能显示或调用服务，不能直接编辑持久状态。

#### 强制测试

1. v21 到 v22 迁移：固定默认值、无运行状态泄露、重复加载稳定。
2. 12 人名册和数据文件双向集合相等。
3. 每类委托的接取、完成、失败、放弃、重复领取、跨日。
4. 送礼成功/物品不足/绑定物品/重复请求，无状态污染。

## 7. 交付报告格式

2. 新增、修改、删除文件的绝对路径。
3. 数据与存档：字段、默认值、迁移、兼容性、版本变化。
4. 生产路径：用户操作 → UI/对话/输入 → service → 状态变化 → 保存。
5. 本地版本借鉴、单机原创扩展、evidence_gap 的清晰分类。
6. 正向、真实变异负向、相邻回归、全量测试、冒烟的实际命令与输出摘要。
7. DeepSeek V4 Flash 的批量工作、输入、输出、复核方式与未闭合缺口。
8. 性能限制、已知问题、下一版本依赖。
9. 明确声明：开发流程和自动化验收仅使用纯文本输入、代码、数据、资源路径、节点属性、运行时状态和日志。

“测试通过”不能替代可重复的代码和日志。PM/SE 必须独立审阅代码、数据、测试、关键状态机和变异负向是否走同一验证器。
