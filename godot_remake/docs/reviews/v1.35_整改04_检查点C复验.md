## 0. C轮返工复验（2026-07-30）

本轮已关闭前次两项问题：

- 测试代码中已不再调用 `_world_action_route()`；世界实体 action 通过真实 `_dispatch_world_action()` 分派。
- world action 循环已精确断言 `code == "OK"` 与 `actual_route == expected_route`，并覆盖 six routes：`battle`、`mine`、`lottery`、`war_soul`、`territory`、`npc_dialogue`。
- 独立复跑专项及六项相邻场景均为退出码 0、各有 1 个 PASS 标记，未见 `SCRIPT ERROR`、`Assertion failed`、`Parse Error` 或 `FAILED`。每个 Godot 进程均打印“Failed to read the root certificate store”环境告警，不能作为测试失败。

但以下两项仍阻断签署。

### C-03：11个 dialogue action 没有被实际验证

当前代码对每个 `dialogue_action_list` 元素仅执行：

```gdscript
main._handle_dialogue_action(da_id)
dialogue_verified += 1
```

随后只断言计数等于列表长度。无论 handler 是空实现、路由错误还是没有任何可观察效果，该循环都会通过。因此“dialogue action独立验证（11个）”的报告结论不成立。

整改要求：为这11项逐项登记并断言预期结果。例如 buy/sell 断言对应商店与模式，`warehouse`/`pets`/`research`/`enhancement`/`quests` 断言对应面板可见，`enter_lottery_room`/`enter_dungeon` 断言地图变更。若某一项预期是只读对话，也须断言对话标题或文本标识。不得用计数自增代替效果验证。

### C-04：两项C负向没有走正向同一验证器，错误码也未被精确断言

`C-neg1` 与 `C-neg2` 在测试内手工 `append()` 字符串到局部数组，再断言 `not ...is_empty()`：

```gdscript
if c_neg1_actual_route != c_neg1_expected:
    c_neg1_errors.append("DISPATCH_ROUTE_MISMATCH:...")
assert(not c_neg1_errors.is_empty(), ...)
```

`C-neg2` 甚至复用 `C-neg1` 的旧 dispatcher 结果，未重新执行同一正向验证路径。这不能证明正向检查器真的会报告 `DISPATCH_ROUTE_MISMATCH` 或 `DISPATCH_CODE_MISMATCH`。

整改要求：抽取一个共用的 `validate_dispatch_result(actual, expected)`（或同等函数）。正向105项循环与两项负向必须都调用它；负向分别篡改 route/code 后，使用 `has_error_code(...)` 精确断言 `DISPATCH_ROUTE_MISMATCH` 与 `DISPATCH_CODE_MISMATCH`。不得继续以手工拼数组及“非空”断言替代。

此外，当前 expected route 仍由一段 `if/elif` 推导而非审查过的显式数据。该结构虽已不再调用旧分类器，但返工时应改为声明式 route 期望表（或注册表字段），避免测试分支与生产分派一同被同样的错误修改。

## 1. 已独立确认的事实

- `scripts/main_original.gd` 的 `_on_actor_input(event, action_id)` 已调用 `_dispatch_world_action(action_id, event)`；`_add_actor()` 的 `gui_input` 信号也仍绑定到 `_on_actor_input`。生产点击接入统一分派这一部分正确。
- `_dispatch_world_action()` 对未知 action 返回 `{ route = "UNSUPPORTED", code = "UNSUPPORTED_ACTION" }`；专项负向用真实 dispatcher 传入 `zzz_unknown_action`，并断言不打开对话、不创建战斗、不改变地图。这个未知 action 隔离分支正确。
- 我独立运行 `res://tests/test_world_interaction_registry_scene.tscn`：进程退出码 0，输出 1 个 `PASS` 标记。运行环境另有 Godot 根证书库读取提示，非本测试断言失败。

## 2. 阻断项 C-01：交付报告与代码不一致

交付报告声称“测试不再单独调用 `_world_action_route()`”。实际 `tests/test_world_interaction_registry_scene.gd` 的全量 route 循环仍执行：

```gdscript
var route: String = main._world_action_route(aid)
if route != "UNSUPPORTED" and not route_representatives.has(route):
    route_representatives[route] = aid
```

这不是措辞差异，而是可直接核验的不实陈述。报告必须更正；今后不得将“仍在调用”写成“已经不再调用”。

## 3. 阻断项 C-02：全量 route 验证没有证明分派结果一致

同一循环对 dispatcher 的唯一断言是：

```gdscript
assert(route_code != "UNSUPPORTED_ACTION", ...)
```

它没有断言 `dispatch_result["route"] == route_key`，也没有为每个 route 验证实际面板、战斗、地图或资源状态差。因此测试无法发现以下回归：分类器把 action 标为 `mine`，生产 dispatcher 实际误走 `npc_dialogue`，只要 code 仍是 `OK`，当前测试依然通过。

这不满足任务书第 4 节“全量action测试必须证明 route 与实际执行分支一致”，也不满足第 10.3 节“同时验证返回的 route/code 与对应状态差”。

## 4. C轮返工要求

1. 全量世界实体 action 的预期 route 不得由 `_world_action_route()` 生成后再拿来验证 dispatcher。可在测试数据中显式登记 `action_id -> expected_route`，或由注册表增加经过审查的 `expected_route` 字段；两者均须覆盖所有非空 world entity action。
2. 对每个 action 调用真实 `_dispatch_world_action()` 或真实 actor input，精确断言：`code == "OK"` 且 `result.route == expected_route`。不得只写“不是 UNSUPPORTED”。
3. 每个实际 route 至少保留一个端到端状态差：
   - `battle`：session 与目标 ID；
   - `mine`：背包数量变化；
   - `lottery`：魔石变化；
   - `war_soul`、`territory`、`npc_dialogue`：可观察面板/剧情状态。
   dialogue action 若由 `_handle_dialogue_action()` 负责，必须与 world actor action 分开清单及测试，不能被 dispatcher 循环假装覆盖。
4. 新增两个精确负向：篡改一个预期 route 必须得到 `DISPATCH_ROUTE_MISMATCH`；篡改一个成功 code 预期必须得到 `DISPATCH_CODE_MISMATCH`。均需调用与正向相同的 runner。
5. 交付报告须提供：world action 总数、已逐项比较总数、dialogue action 独立总数、每类状态差、两项负向错误码、专项及相邻复验结果。
