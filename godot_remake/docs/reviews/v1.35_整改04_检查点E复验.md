### E-R1：48个runtime availability规则中有15个明确错误

独立将注册表与`GameState.can_enter_map()`逐项对照，发现15项不一致：

| map → target | registry当前值 | 生产实际条件 |
|---|---|---|
| palace → palace_garden | `always` | 爵位等级必须大于0 |
| dungeon → dungeon_floor_2 | `story_flag:dungeon_floor_1_cleared` | `unlocked_maps.dungeon_floor_2` |
| dungeon_floor_2 → dungeon_floor_3 | `story_flag:dungeon_floor_2_cleared` | `unlocked_maps.dungeon_floor_3` |
| dungeon_floor_3 → dungeon_floor_2 | `story_flag:dungeon_floor_1_cleared` | `unlocked_maps.dungeon_floor_2` |
| ice_palace → ice_border | `story_flag:king_rescued` | 周五或已救国王 |
| ice_border → demon_camp | `always` | 已救国王 |
| demon_camp → ice_border | `story_flag:king_rescued` | 周五或已救国王 |
| demon_camp → demon_left/right | `always` | 已救国王 |
| demon_camp → demon_banner | `story_flag:demon_commander_defeated` | 已救国王 |
| demon_left/right/banner → demon_camp | `always` | 已救国王 |
| demon_banner → energy_tower | `story_flag:demon_commander_defeated` | `demon_campaign.commander_alive == false` |
| energy_tower → demon_banner | `story_flag:demon_commander_defeated` | 已救国王 |

其中`dungeon_floor_*_cleared`与`demon_commander_defeated`并不是当前`story_flags`字段。报告将这些值描述为“可用性规则字符串”但没有核对生产实现，属于实质性数据错误。

### E-R2：validate_exits完全没有读取runtime_availability_rule

当前验证器只使用`GameState.can_enter_map(target)`计算disabled。即使把registry中的`runtime_availability_rule`全部改成任意字符串，专项仍会PASS。因此本轮新增字段只是未受保护的说明文字，不构成“注册表→生产规则→metadata/按钮”的一致性闭环。

整改要求：

1. 在生产侧增加稳定的只读规则标识方法，例如`GameState.map_entry_availability_rule(map_id)`；最好让`can_enter_map()`依据同一标识分派，避免两套映射漂移。
2. 使用能够精确表达现有逻辑的标识，例如：`level_only`、`nobility_rank_gt_0`、`unlocked_map:<id>`、`friday_or_king_rescued`、`king_rescued`、`commander_defeated`。
3. 修正48项registry规则，验证器逐项断言`registry.runtime_availability_rule == GameState.map_entry_availability_rule(target)`，再验证当前fixture下`button.disabled == world_disabled == not can_enter_map(target)`。
4. 新增负向：篡改一个registry runtime rule，调用同一`validate_exits()`，精确命中`EXIT_RUNTIME_RULE_MISMATCH`；恢复后空错误列表。

完成后重新提交E复验。不得以现有三项PASS作为规则正确的证据，因为这三项测试当前不会读取该字段。

## 2. E-01：world_direction仍然只检查存在

任务书第7节明确要求：

```text
world_direction == registry direction
```

当前`validate_exits()`仅执行`has_meta("world_direction")`，没有比较值。交付报告也明确写成“存在检查”，因此“7个metadata逐项比较实际值”的总标题与实现不一致。

整改要求：定位当前target对应的registry出口，断言`btn.get_meta("world_direction") == exp_ex.direction`。新增负向篡改direction metadata，使用同一`validate_exits()`精确命中`EXIT_METADATA_VALUE_MISMATCH:world_direction`，恢复后验证无错误。

## 3. E-02：运行时规则没有登记进注册表

任务书第7节与10.6节要求在保留SWF evidence gap的同时，为每个出口新增：

- `runtime_required_level`
- `runtime_availability_rule`

当前48个出口仍只有`required_level: "UNCONFIRMED"`与`availability: "UNCONFIRMED"`；注册表中没有上述runtime字段。验证器直接向GameState取值，无法证明“注册表→runtime metadata→按钮状态”三者一致。

整改要求：48个出口逐项登记具体`runtime_required_level`及稳定的`runtime_availability_rule`，不得覆盖原版`UNCONFIRMED`字段。验证器以注册表runtime字段为预期，并交叉核对GameState规则、metadata及`button.disabled`。

## 4. E-03：metadata预期值没有全部来自registry

当前`world_action_route`与`world_current_map`分别和硬编码`"edge_exit"`、`GameState.current_map_id`比较；`world_direction`则完全未取registry值。任务书要求与registry字段比较。

整改要求：

- current map预期取`reg_map.map_id`；
- direction预期取当前出口`direction`；
- action route预期取当前出口`action_route`；
- target预期取当前出口`target_map_id`。

然后再将这些registry预期与按钮属性及metadata双重比较。这样才能发现registry、GameState和节点中任一方漂移。

## 5. E-04：gap复合键只做单向检查，且模糊子串兜底会掩盖错误

任务书第10.7节要求将“未确认字段集合”和“结构化gap字段集合”做双向集合比较。当前实现只检查未确认字段是否能找到gap，没有检查多余、过期或错误gap；并在精确键未命中后使用：

```gdscript
field_name in str(g.get("field", ""))
```

该子串匹配可能把错误字段误判为覆盖，例如`level`可被`required_level`命中，破坏字段级精确性。

整改要求：删除模糊子串兜底。分别构造`unconfirmed_field_keys`与`gap_field_keys`，做双向集合差：

- 未确认字段缺gap → `GAP_FIELD_UNCOVERED:<compound_key>`；
- gap没有对应未确认字段 → `GAP_FIELD_EXTRA:<compound_key>`。

48个出口的availability与required_level必须产生96个精确复合键，并逐项双向匹配。
