## 1. 目标与边界

实现完全离线、单人可玩的商会经济循环。所有交易对象均为本地固定 NPC 或系统货架，不连接网络，不存在实时玩家、不存在真实货币、不存在付费抽取。

本版本完成：

1. 商会声望与商会等级。
2. 与固定冒险者的直接交易请求。
3. 拍卖行的挂单、竞价、流拍、结算、邮件领取和审计账本。
4. 每日普通货架、每周主题货架、拍卖目录的确定性刷新。
5. 真实 UI/NPC 入口、状态提示和账单明细。

本版本不做：

1. 新地图、新主线、新 Boss、新装备数值体系。
2. 网络匹配、跨存档交易、真实玩家、聊天或货币充值。
3. 可无限套利的买卖循环；不能通过重复打开面板或重复回调增加金币、魔石、物品或声望。
4. v1.47 的产业、城堡和领地产出。

## 2. 体验流程

玩家在现有商会/收藏家/杂货商关联入口中打开“商会事务”。流程必须是：

1. 查看本日货架、商会声望、可用交易名额和当前拍卖。
2. 接受某个固定冒险者的交易请求，或向其发出交易。
3. 选择物品、数量、报价，确认后生成不可变交易单。
4. 打开拍卖行，查看待售条目、竞价上限、剩余日数和历史结果。
5. 出价或挂单；日结时统一结算；通过邮件领取成交物或退回物。
6. 任一失败必须给出可解释文本，且没有资源变化。

商会不可成为“无限送钱按钮”。所有资源变化必须有 operation_id、账本记录和幂等保护。

## 3. 数据合同与服务边界

### 3.1 新增数据文件

1. `data/market_rules.json`
   - 每日刷新时刻、普通货架上限、主题周规则、声望阈值、手续费规则、交易次数规则。
2. `data/market_catalog.json`
   - 可交易物品白名单、基础估值、最小/最大报价、是否允许直接交易、是否允许拍卖。
3. `data/auction_rules.json`
   - 挂单期、最低加价、流拍规则、竞价退款、成交税和成交邮件模板 ID。
4. `data/adventurer_trade_profiles.json`
   - 仅引用 v1.43 固定 NPC ID；登记偏好、厌恶、每日可交易次数、报价倾向和声望要求。

所有 ID 必须唯一。数据文件不得以 UI 文案或硬编码 if/else 作为规则源。

### 3.2 新增服务

1. `MarketService`
   - 生成当日货架；创建和执行直接交易；计算声望变化；写入市场账本。
2. `AuctionService`
   - 创建挂单、出价、取消、日结、成交/流拍结算和邮件投递。
3. `EconomyLedgerService`
   - 为每一次资源变化生成 operation_id、前后余额、原因、关联订单 ID；提供幂等查询。
4. `MarketSnapshotService`
   - 将每日种子、目录版本和 NPC 关系快照固化到订单，禁止结算时重新读取可变状态。

服务层必须返回结构化结果：`success`、`code`、`operation_id`、`message_key`、`state_delta`。UI 不得自行扣钱、加物品或决定成交结果。

### 3.3 v22 存档字段

在现有 `expansion_state` 下新增或补齐以下可选字段，并用固定默认值兼容旧 v22 档：

1. `market.reputation`、`market.reputation_level`、`market.last_refresh_day`。
2. `market.daily_catalog`、`market.weekly_theme`、`market.daily_seed`。
3. `market.trade_orders`、`market.auction_listings`、`market.auction_bids`。
4. `market.ledger`、`market.next_operation_id`、`market.next_listing_id`。
5. `market.settled_operation_ids` 与 `market.claimed_mail_ids`。

保存后读取必须深比较所有上述字段；损坏、缺字段、未知物品、重复 ID、负数、非法枚举均须拒绝或回退到明确默认值，且不得半提交内存。

## 4. 经济规则

### 4.1 每日货架

1. 使用 `day + save_seed + catalog_version` 生成确定性目录；同一存档同一天反复打开完全一致。
2. 普通货架最多 6 项，主题货架最多 2 项；物品必须来自白名单。
3. 每周主题由固定星期和固定种子决定；不得依赖系统随机数的隐式状态。
4. 每日刷新只在真实日结后发生一次；重复加载、重复进入地图、重复结算不得重复刷新或重置购买次数。

### 4.2 直接交易

1. 交易双方必须为玩家和已解锁固定 NPC；不能对不存在、未解锁、离场或冷却中的 NPC 交易。
2. 价格由物品估值、NPC 偏好、关系、商会声望和本日目录快照组成；结果写入订单后不可漂移。
3. 扣除物品与给付物品必须是同一原子操作；任一步失败则双方状态均不变。
4. 每个 NPC 每日交易上限来自数据；被拒绝交易不消耗次数。
5. 交易成功可影响关系和声望，但必须在数据规则定义的上限内。

### 4.3 拍卖行

1. 挂单时先将玩家物品转入 escrow，生成 `listing_id` 与 `operation_id`；成功前不得从背包删除。
2. 出价时冻结出价资源；新出价成功后，旧最高出价的冻结资源必须只退回一次。
3. 一人离线单机拍卖只允许固定 NPC 使用其日结快照竞价；不能凭空生成任意竞价者。
4. 日结后：成交则给卖方款项并通过邮件交付物品给买方；流拍则退还 escrow 物品；取消仅在无有效竞价时允许。
5. 任一 listing 只能结算一次；延迟回调、旧 session、重复加载后的补偿不能重复结算。
6. 手续费、成交税、退款必须全部记入账本，金额不得为负。

## 5. UI 与交互要求

1. 使用既有面板体系新增商会面板和拍卖面板，不修改顶部 HUD 布局，不把长列表塞入 HUD。
2. 面板至少分为：今日货架、直接交易、拍卖列表、我的挂单、交易账本、邮件领取。
3. 长列表必须有分页或滚动；空状态、锁定状态、余额不足、物品不足、冷却、流拍和已结算都有文本原因。
4. 从真实 NPC 对话 action 或既有商会入口进入；不得仅由测试直接 `new` 面板绕过生产路由。
5. 所有确认按钮防重复：第一次成功后立即更新可点击状态；重复 pressed 只能得到幂等结果或明确错误码。
6. 新面板启动默认隐藏；边界、层级、状态提示和关闭路径必须纳入代码型 UI 审计。

资源限制：优先复用现有 UI 框、按钮、格子和文本样式。若确实需要新增资源，只能引用 v1.42 资源登记中已批准的本地路径；本版本不得整包导入 2.x 资源。

## 6. 强制测试

### 6.1 正向测试

至少建立 `test_market_auction_scene`，并覆盖：

1. 同存档同日目录稳定，跨日真实日结后目录按规则变化一次。
2. 六项普通货架、两项主题货架上限和白名单约束。
3. 与两名不同固定 NPC 的直接交易成功，关系/声望/账本变化准确。
4. 交易拒绝时金币、魔石、背包、关系、声望、次数和账本零变化。
5. 挂单、固定 NPC 竞价、抬价、退款、成交、流拍和邮件领取的完整真实路径。
6. 同一 listing 的二次结算和同一邮件的二次领取均保持幂等。
7. 读档后订单快照、账本、escrow、冻结资源和领取状态深比较一致。
8. 真实 UI 路由：NPC 对话进入、面板切换、确认、关闭和状态提示。
9. v1.43-v1.45 的关系、日结、排行榜、擂台与邮件相邻回归。

### 6.2 必须有的真实变异负向

至少 12 项；每项必须先断言变异实际生效，再调用正向同一验证器并命中精确错误码：

1. 不在目录白名单的 item_id。
2. 负数或超上限报价。
3. 不存在/未解锁 NPC。
4. 同一个 operation_id 重复执行。
5. 同一个 listing_id 重复结算。
6. escrow 物品与挂单快照不一致。
7. 旧最高出价退款两次。
8. 交易冻结资源不足。
9. 订单快照的 catalog_version 与当前规则不兼容。
10. 日结回调后再以旧日期刷新。
11. 账本金额与状态变化不一致。
12. 损坏存档中的重复 listing_id 或 claimed_mail_id。

错误码应采用 `MARKET_`、`AUCTION_`、`LEDGER_` 或 `SAVE_` 前缀，禁止只断言错误列表非空。

1. 新场景接入 `run_tests.ps1` 后，更新测试数量的单一来源和文档门禁；禁止仅手写修改多个数字掩盖差异。

## 7. 拒签条件

出现任一项即拒签：

1. 商会或拍卖可无限增加资源，或扣除与给付不是同一原子操作。
2. 用随机临时值、硬编码排名/价格或 UI 文本代替存档化数据规则。
3. 竞价、退款、成交、邮件领取不能幂等。
4. 订单结算读取了发起后发生变化的 NPC 状态，而非快照。
5. 测试直接改终态、直接塞账本或直接创建成功订单来冒充真实流程。
6. 以非纯文本附件作为开发或验收输入。
