## 1. 目标

对 v1.42–v1.54 的单机长线内容进行数据平衡、长流程验证、存档兼容、发布包和文档收束。该版本以修复和验证为主，只允许在可量化证据支持下调整数值；不得借机重做主线、重置用户数据或添加未计划大功能。

候选验收目标：新档可完成主线与至少一个赛季循环；旧 v21/v22 档安全读取；高版本/损坏档安全拒绝；发布包/清单/文档一致；长流程无重复发奖、无存档损坏、无泄漏。

## 2. 平衡审计合同

### 2.1 新增文件

1. `docs/balance_audit_v155.json`：每个调整项的原值、候选值、来源、理由、受影响系统、上/下限、测试 ID、批准状态。
2. `docs/long_flow_matrix_v155.json`：新档、旧档、终局档、赛季档、资源紧张档等流程夹具定义。
3. `docs/release_candidate_manifest_v155.json`：候选包、版本、构建命令、产物、哈希、测试证据路径。
4. `tests/fixtures/` 下的文本型 JSON 夹具；禁止用隐式用户目录残留充当夹具。

### 2.2 数值保护

以下用户已经确认的覆盖值必须逐项对照，未经独立任务批准不得修改：

1. 杂货商金币、收藏家魔石的用户设定。
2. 人物经验倍率、军功/Boss 奖励倍率。
3. 品质/魔魂必成、战魂加成与战魂晶石成功率。
4. 玫瑰好感度倍率、研究所技术上限/产量规则。
5. 技能书与月光宝盒掉率等既有覆盖规则。

审计必须证明调整没有意外覆盖、双重应用或回退这些规则。

## 3. 长流程矩阵

至少建立以下 10 条确定性流程，每条使用固定文本夹具、真实生产入口和真实保存加载：

1. 新档：基础城镇 → 第一战 → 背包/商店 → 皇宫/日常。
2. 旧 v21 档：加载、默认扩展状态、保存为 v22、再次加载。
3. v22 中期档：固定冒险者 → 商会交易 → 排行/擂台。
4. 领地档：占领 → 日结 → 城堡/委任 → 事件。
5. 树心/港口档：分支、Boss、周常。
6. 边境/冰原档：补给、元素、Boss、读档。
7. 终局档：深渊 → epilogue → completed → 周常。
8. 挑战/装备/幻兽档：奖励、精通、支援、研究所合同。
9. 赛季档：连续 14 日 → 结算 → 新赛季 → 历史。
10. 资源紧张/背包满/损坏档：失败无副作用、恢复和清理。

每条必须定义起点快照、真实操作、预期状态差、保存点、重载点、幂等点、结束快照；不能只运行脚本后打印“成功”。

## 4. 平衡规则

1. 调整前必须建立基线：新档、适中档、后期档每种至少一条真实流程的耗时、资源收支、失败率/门槛和奖励数量。
2. 每个数字改动必须有 `audit_id`，并注明不会影响的用户覆盖值；禁止无来源的“感觉太慢/太快”硬改。
3. 所有收益源都应有日/周/一次性上限或可解释的重复规则；用账本审计总入账。
4. 所有消耗源必须保证失败不吞资源，成功只结算一次。
5. 挑战难度、Boss 数值、商会价格、领地产量、赛季奖励之间不得形成无上限套利闭环。
6. 若发现结构性不平衡但无法安全解决，登记 P0/P1 gap，不以秘密数据改动掩盖。

## 5. 存档、性能、测试与发布

### 5.1 存档兼容

1. v21、最早 v22、当前 v22、损坏档、未来版本档都必须使用真实 `load_game` 路径测试。
2. v21 必须按既有默认/迁移契约加载，保存后为当前 v22；不得丢失核心字段。
3. 高版本档必须拒绝且内存不变；损坏档恢复/拒绝策略必须可审计。
4. 连续保存、异常恢复、tmp/bak/final 文件矩阵按既有保存完整性测试重新运行。

### 5.2 性能与生命周期

1. 以既有 700×550 逻辑视口和现有主场景为基线，测试切图、面板、战斗、赛季 rollover、长流程后的对象释放。
2. 统计每条长流程的 ObjectDB 泄漏、未结束协程、悬挂 timer/tween、临时目录和 user:// 测试残留。
3. 不以增加 `quit-after`、静默跳过或屏蔽错误来掩盖超时/泄漏。

### 5.3 发布候选

1. 代码/数据/文档定稿后重新导出 PCK/EXE。
2. 生成 manifest 后再生成 SHA256SUMS；三方验证每个实际文件、无缺失、无多余、无重复行。
3. 真实自然退出冒烟：哈希、APP_READY、退出码、日志错误标记、ObjectDB 均通过。
4. 运行 doc gate、release gate 和它们的真实负向变异；任何跳过/临时残留均失败。

## 6. 强制测试

### 6.1 正向

1. 10 条长流程按 JSON 矩阵数据驱动遍历，注册表—执行集合双向相等。
2. 用户覆盖值逐项与 v1.41 签署基线对照，无意外变化/双重应用。
3. 所有扩展系统的每日、每周、一次性奖励账本总额与真实状态变化一致。
4. v21/v22/损坏/未来版本档的真实保存加载和内存不变验证。
5. 连续至少 30 天游戏日与两轮 14 日赛季；随机种子固定，可复现。
6. 全量 runner 至少连续两次通过；主场景冒烟、doc gate、release gate、发布包验证通过。
7. 在普通用户账户环境复跑完整候选门禁；若环境不可用，明确阻断，不得宣称完成。

### 6.2 真实变异负向

至少 20 项，覆盖：

1. 删除/篡改平衡审计项。
2. 用户覆盖值被意外回退或二次乘算。
3. 任一日/周/一次性 operation_id 重复。
4. 资源账本与状态差不一致。
5. v21 核心字段丢失。
6. v22 新字段非法类型/范围。
7. 未来存档版本被接受。
8. tmp/bak/final 恢复错误。
9. 长流程步骤被跳过或伪造终态。
10. 赛季重复 rollover。
11. 跨系统套利闭环。
12. 运行中对象/协程泄漏。
13. runner 缺 PASS、包含 SKIPPED、错误日志未捕获。
14. 发布包/manifest/SHA 重复、缺失、错误。
15. 冒烟 APP_READY 缺失、早退、超时、日志含错误。
16. doc gate 场景数/状态/哈希不一致。

每项先证明变异，再调用同一生产/验证入口命中精确错误码；不得以手写布尔结果冒充门禁。

## 7. 拒签条件

任一项拒签：

1. 未经批准修改用户覆盖值或只提供“看起来合理”的数值说明。
2. 长流程由终态夹具伪造，未走真实生产操作。
3. 存档兼容、原子保存、高版本拒绝未独立复验。
4. 全量/门禁只是开发报告，缺少可复运行命令和日志证据。
5. 发布包哈希与当前代码/数据不对应。
6. 存在 ObjectDB 泄漏、未结束协程、临时残留或 `PASS SKIPPED`。
7. 使用非纯文本输入执行或验收。
