## 1. 目标与范围

实现完全离线的十四日赛季和终局后世界事件，提供可长期回访的短循环，而不伪装成在线运营。赛季由单机存档日期、固定种子、固定 NPC 行为表和已完成内容决定；没有服务器、没有真实排行榜、没有付费通行证。

本版本完成：

1. 14 天一个周期的赛季状态机。
2. 每日公告、固定 NPC 动态、精选委托、有限奖励和世界回顾。
3. 商会、领地、挑战、幻兽、深渊和排行榜的轮换入口。
4. 终局后分支回顾、固定 NPC 关系小事件、赛季收藏目标。
5. 至少两套可复现赛季主题（数据驱动），但不要求大量新地图。

不做：联网赛季、服务器时钟、实时活动、无上限每日奖励、现实货币商品或强制登录。

## 2. 数据与状态

### 2.1 新增数据文件

1. `data/season_rules.json`：周期长度、日序、奖励上限、重置、补偿和时间来源。
2. `data/season_themes.json`：至少两个主题、每日事件池、加成范围、禁用组合、文本 key。
3. `data/season_contracts.json`：委托 ID、来源系统、前置、目标、奖励白名单、重复规则。
4. `data/season_npc_schedules.json`：固定 NPC 的季节对话/可用性/邮件，引用既有 NPC ID。
5. `data/season_rank_rules.json`：单机排行榜赛季分数来源、同分规则和结算记录。

所有日序/主题/委托/奖励均使用稳定 ID；数据必须可验证，不允许在 UI 里写 14 天分支。

### 2.2 v22 状态

`expansion_state.season` 至少包括：

1. `season_id`、`theme_id`、`day_index`、`start_day`、`seed`。
2. `daily_contract_ids`、`completed_contract_operation_ids`、`claimed_reward_ids`。
3. `npc_schedule_snapshot`、`season_rank_snapshot`、`epilogue_event_ids`。
4. `last_rollover_day`、`ledger`、`history`。

赛季状态不能依赖操作系统当前时间；只能从已存档的游戏日与已有真实日结 API 推导。

## 3. 核心规则

### 3.1 周期与日结

1. 第 1–14 天由 `start_day` 和游戏日差计算；日结最多推进一次，重复加载不会重复发奖或跳天。
2. 日序 14 结束时结算赛季摘要并进入下一赛季；历史最多保留数据定义的固定条数，防止存档无限膨胀。
3. 主题、每日委托、固定 NPC 日程和排名快照由 `season_id + seed` 固化；同一日反复读取一致。
4. 改系统日期、重启进程、切地图、打开面板均不能改赛季。

### 3.2 委托和奖励

1. 每天至多 3 个委托，来源可来自已经签署的商会、领地、挑战、幻兽、边境、冰原和深渊系统。
2. 委托只能读取真实生产状态；不得复制一套伪任务计数器。
3. 奖励有每日、赛季、主题三种上限，全部写 operation_id/ledger；训练/回顾模式不增加赛季分数。
4. 完成后可显示回顾/榜单变化，但不能通过重复交付、重复邮件或重新加载重新奖励。

### 3.3 终局后事件

1. 事件仅在 `abyss_finale.completed` 后解锁，且不反写或重置最终主线。
2. 至少 8 个固定 NPC 小事件，使用关系、领地、商会、收藏或挑战的真实状态作为分支输入。
3. 事件可以改变关系/小型资源/回顾记录，但必须有固定上限、可解释原因和幂等保护。

## 4. UI 和入口

1. 通过现有公告栏、任务簿、固定 NPC 对话或底栏明确入口打开赛季簿。
2. 页面包含：今日、十四日历、主题、委托、固定 NPC 动态、赛季榜、奖励、历史回顾。
3. 未解锁终局后事件、次数耗尽、已领取、系统状态异常均须显示文本原因。
4. 不改顶部 HUD 几何；面板默认隐藏、可关闭、不遮挡状态提示，且纳入现有代码型 UI 审计。

每项先证明变异，再调用正向同一验证器，命中精确 `SEASON_`、`CONTRACT_`、`EPILOGUE_`、`RANK_`、`LEDGER_` 或 `SAVE_` 错误码。
