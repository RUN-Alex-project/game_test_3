## 1. 整改目标

修复 `docs/reviews/v1.35_验收评审.md` 中 QA-135-01 至 QA-135-05、DQ-135-01 至 DQ-135-02。

整改完成后，修改注册表中的任一关键实体、出口、动态期望或证据token，专项测试都应可靠失败；活动运行时与注册表出现增删、资源漂移、坐标漂移、尺寸漂移、action漂移或kind漂移时也应可靠失败。

## 2. 证据文件整改

继续使用：

`docs/evidence/world_interactions_v103_v9.txt`

### 2.1 不得只列命令名

对实际确认的内容，必须保存可复核的反查结果token。每张地图按实际证据记录：

- SWF根帧或sprite scope。
- 背景角色。
- 出口PlaceObject角色、方向、目标、矩阵、位置和尺寸。
- NPC、怪物、交互物、装饰的角色号。
- 原始位置和边界/尺寸。
- ActionScript字符串或动作token。
- 动态出现条件token。

必须写明实际执行命令、源SWF文件名和对应scope。不能用 `main_original.gd`中的当前运行时数值冒充SWF证据。

### 2.2 未确认字段处理

本整改不要求凭猜测消灭所有 `UNCONFIRMED`，但必须区分：

- 运行时当前值。
- 原版证据状态。

注册表用于运行时比较的 `position`、`size`、`direction`、`availability`等字段必须保留具体当前值；另用 `evidence_status`、`field_evidence`或等价结构表示是否被SWF确认。不得把运行时必需字段直接替换成字符串 `UNCONFIRMED`，导致无法测试运行时。

任何关键字段未被独立证据确认时：

- 实体/出口分类不得为 `native_confirmed`，除非schema明确做到逐字段分类且测试能阻止未确认字段冒充已确认。
- 在结构化 `evidence_gaps`中登记map ID、对象ID、字段名、缺失证据和建议反查命令。
- 不得只保留“28图待确认”一条无法定位的宽泛说明。

### 2.3 token自动验证

专项测试必须断言：

- `evidence_source`存在且可读取。
- 每个 `evidence_token`均能在对应证据文件命中。
- `native_confirmed`对象的证据来源不是其 `implementation_source`。
- `implementation_source`存在。
- classification/evidence_status合法且与缺口登记一致。

若一个通用token无法唯一支持对象，应改用包含角色号、地图scope或坐标的组合token，不得用泛化的 `battle`、`handler`等词自证。

## 3. 运行时稳定metadata

在不改变视觉或交互行为的前提下：

### 3.1 装饰

- `_add_decoration()`必须接收或生成显式稳定 `entity_id`。
- 每个装饰节点同时设置 `world_entity_id`和 `world_entity_kind=decoration`。
- 各调用点的ID必须与注册表一致。
- 不得依赖子节点顺序匹配装饰。

### 3.2 演员

- `_add_actor()`应允许显式传入稳定entity ID和kind，或采用同等可靠方案。
- 运行时 `world_entity_id/world_entity_kind`必须与注册表一致。
- 不得仅凭action字符串启发式推断所有语义种类。
- NPC、monster、interactive_prop分类必须按对象职责复核。

### 3.3 出口

每个可见 `NativeExitButton`至少提供：

- 稳定出口ID。
- `world_entity_kind=exit`。
- 当前地图。
- direction。
- target map ID。
- availability/required level的可审计值或等价数据。

## 4. 28图精确运行时测试

扩展现有：

`tests/test_world_interaction_registry_scene.gd`

不新增第51个场景。

对28张地图逐一设置隔离的基准GameState夹具，调用活动主场景 `_apply_current_map()`，并精确比较注册表与运行时：

- 当前地图背景资源。
- 可见出口精确集合。
- 每个出口的ID、方向、目标、位置、尺寸、可用状态和等级门槛。
- 实体精确集合，既不能缺少，也不能多出未登记节点。
- 每个实体的ID、kind、资源路径、position、size和action ID。
- 装饰必须参加比较，不能直接 `continue`。
- 所有比较使用稳定ID，不使用子节点顺序。

动态实体不能混入“always”基准集合。测试应根据 `appearance_condition`或场景关联明确计算该状态的期望集合。

### 4.1 边界规则

- 默认断言交互实体位于700×512地图可玩区域。
- 如果SWF原始坐标确实延伸到顶部HUD或底栏覆盖区，在注册表为该对象登记显式 `native_overlap_exception`或等价字段，并提供可命中的SWF坐标token。
- 只有登记并验证过的对象可使用例外；不得统一放宽为y=550。
- 纯装饰至少要检查其登记边界与运行时一致，并确认 `mouse_filter=IGNORE`。

## 5. 动态场景注册表与参数化测试

填充顶层 `dynamic_scenarios`，不得为空。

每个scenario至少包含：

- 稳定scenario ID。
- map ID。
- 明确的GameState夹具。
- `expected_present`精确实体ID集合。
- `expected_absent`精确实体ID集合。
- 必要时的出口期望。
- 对应证据或已登记的evidence gap。

至少覆盖原任务书第7节全部状态：

1. 皇宫国王未救/已救。
2. 五福娃各候选地图使者、草原战斗、草原2领奖、树心城五福娃与最终使者的前后状态。
3. PK未报名、60/100/130组Boss、击败后不重复出现。
4. 战魂谜宫箱子未点、守卫出现、秘密完成。
5. 领地未达爵位、可挑战、临时挑战者、已占领；所有实际领地地图均参数化。
6. 最终战中军守卫、突击队、左军图腾、右军神秘部队、主帅、魔的能量及通关后不再生成。
7. 公主/侍女、研究所和其他已有条件演员。

专项测试读取 `dynamic_scenarios`逐项执行，比较精确出现/缺失集合。每项前后必须重置或恢复GameState，不能依赖测试执行顺序。

已有 `test_fuwa_scene`等专项继续作为相邻回归，但不能替代上述统一参数化测试。

- 所有非空action ID必须能归一化到有效handler、monster ID或明确的专属路由。
- 未知action必须令测试失败。

至少各执行一条真实路径：

- 普通NPC对话。
- 商店。
- 仓库。
- 研究所。
- 普通怪物。
- Boss。
- 领地报名官。
- 矿点。
- 抽奖箱。
- 战魂箱和守卫。
- 地图边缘出口。
- NPC传送。

应验证预期面板、对话、战斗session或地图变化，不能只断言函数存在。

## 7. 必做负向验证

整改报告必须给出以下临时破坏实验的实际失败信息，并在验证后完整恢复：

1. 删除或新增一个注册表实体，逐图精确集合测试失败。
2. 修改一个实体position或size，运行时比较失败。
3. 把一个evidence token改为不存在的token，证据测试失败。
4. 修改一个dynamic scenario的 `expected_present`，动态测试失败。
5. 移除一个装饰的 `world_entity_id`，metadata/集合测试失败。
6. 把一个action ID改为无handler值，可达性测试失败。

恢复后必须确认无临时文件、临时注册表值或修改后的GameState残留。
