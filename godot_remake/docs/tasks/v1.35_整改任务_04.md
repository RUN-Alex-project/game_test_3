## 1. 禁止扩大范围

保留整改03中已经正确完成的代码，只修本任务列出的八项。

不得重新生成整个注册表，不改玩法数值、地图拓扑或存档结构。

## 2. 动态期望必须真正独立

新增只返回always实体的helper，例如：

`expected_always_entity_snapshot(reg_map)`

它必须：

- 只包含 `appearance_condition == "always"`。
- 不读取GameState。
- 不调用 `_condition_active()`。

动态scenario期望只能是：

`expected_always_entity_snapshot + expected_dynamic_present`

测试必须验证：

- present与absent无交集。
- 该地图所有非always实体恰好出现在present或absent之一。
- present/absent中的ID都真实存在于该地图注册表。
- 漏写任一条件实体立即失败。

删除动态循环中对 `expected_entity_snapshot()`的调用。

## 3. 领地六图四态

六张领地地图逐图参数化执行：

1. rank_low：
   - `begin_territory_challenge()`返回rank_too_low。
   - 无临时挑战者。
2. rank_ok：
   - status available。
3. challenger_active：
   - 调用真实 `_start_territory_challenge(map_id)`。
   - 出现正确 `battle:territory_*_guard`。
   - kind/action/asset/position/size正确。
   - battle session锁定正确challenger ID。
4. owned：
   - resolve victory。
   - owned_territory等于map ID。
   - 临时挑战者从场景移除。
   - 报名官对话反映已占领状态。

可以在registry增加 `territory_action_scenarios`或给现有scenario增加steps/outcomes，但六图每图四态必须可机检。

最终展开结果至少24个领地状态，不得再用12个两态case宣称四态完成。

## 4. dispatcher必须接入真实分派

`_world_action_route()`不得继续作为测试专用旁路名单。

至少满足一种：

- `_on_actor_input()`实际调用该route决定分派。
- 或建立统一 `_dispatch_world_action(action_id)`，生产点击和测试都调用它并返回route/result。

unknown action必须：

- 实际传入生产dispatcher。
- 返回或设置明确 `UNSUPPORTED_ACTION`。
- 不打开对话、不战斗、不改地图、不改资源。

全量action测试必须证明route与实际执行分支一致，而不是只调用分类器。

dialogue action如由另一dispatcher处理，应单独验证，不得混入world actor名单伪装覆盖。

## 5. 负向第5和第6项必须真实执行

### 第5项

- 复制一个真实scenario。
- 修改其 `expected_dynamic_present`或absent。
- 调用与正向动态矩阵相同的scenario runner。
- 得到集合错误。

不得直接调用普通实体字典验证器代替scenario runner。

### 第6项

- 使用palace或其他确定含装饰的地图。
- 明确assert找到装饰节点。
- 保存该节点原 `world_entity_id`。
- 临时 `remove_meta("world_entity_id")`。
- 重新执行 `runtime_entity_snapshot()`及正向验证器。
- 得到缺失/metadata错误。
- 恢复metadata。
- 再次验证通过。

禁止使用 `if found`静默跳过。找不到装饰必须立即失败。

## 6. 状态隔离补正

- snapshot/restore增加warehouse，或apply_fixture不得清空未被快照保存的warehouse。
- 每个scenario恢复后对快照中的所有关键字段做deep equality，不得只比较current_map_id。
- action组结束后同样验证level、magic_stones、inventory、warehouse、demon_campaign和territory字段恢复。

## 7. 出口runtime metadata

`NativeExitButton`增加：

- `world_required_level`

验证器必须比较metadata实际值：

- world_entity_id == `exit:<target>`

- world_action_route == registry action_route

## 8. gap字段覆盖

对每个evidence-gap对象：

## 9. 负向与回归门槛

新增或修正负向：

- 漏写conditional实体 → dynamic coverage错误。
- 修改真实scenario期望 → scenario runner错误。
- 实际移除装饰metadata → metadata/集合错误。
- unknown传入真实dispatcher → UNSUPPORTED_ACTION。
- 修改出口metadata值 → 对应EXIT_METADATA_MISMATCH。
- 右侧越界 → OVERLAP_BEYOND_CANVAS。

先由开发模型完成逐项自查，再由PM/SE独立检查代码，确认不存在：

- `if found`跳过必做断言。
- 未使用变量冒充状态差。
- 测试专用旁路冒充生产dispatcher。
- 用条件解释器推导独立期望。

通过静态审查后再运行：

- 专项。
- 关键相邻。
- 50项全量。
- 主场景冒烟。

## 10. SE实现指导

本节不是额外需求，而是完成第2至第9节的推荐实现方法。开发模型应优先沿用现有helper和业务入口，不要重写玩法。

### 10.1 先分清“注册表定义”“测试期望”“运行时结果”

三者必须来自不同路径：

- 注册表定义：描述always实体、条件实体及scenario显式期望。
- 测试期望：只由always实体加scenario的present列表组成。
- 运行时结果：由真实GameState夹具和`_apply_current_map()`产生。

禁止用运行时条件解释器生成测试期望，否则实现和测试会同时犯错。

推荐结构：

```gdscript
func expected_always_entity_snapshot(reg_map: Dictionary) -> Dictionary:
    var result := {}
    for entity in reg_map.get("entities", []):
        if str(entity.get("appearance_condition", "always")) == "always":
            result[str(entity["entity_id"])] = entity.duplicate(true)
    return result

func validate_scenario_partition(reg_map: Dictionary, scenario: Dictionary) -> Array[String]:
    var conditional_ids := {}
    for entity in reg_map.get("entities", []):
        if str(entity.get("appearance_condition", "always")) != "always":
            conditional_ids[str(entity["entity_id"])] = true
    var present := _id_set(scenario["expected_dynamic_present"])
    var absent := _id_set(scenario["expected_dynamic_absent"])
    # 检查交集为空、并集恰好等于conditional_ids。
    # 这里不得读取GameState，也不得调用_condition_active。
    return errors
```

scenario runner的固定顺序：

1. 验证scenario定义的present/absent分区。
2. 保存完整GameState快照。
3. 应用fixture。
4. 调用真实`_apply_current_map()`。
5. 构造`always + present`期望。
6. 与运行时snapshot做双向比较。
7. 对absent逐个断言运行时不存在。
8. restore后对完整快照做deep equality。

### 10.2 状态隔离应做成一个可复用断言

不要在每个循环里只写：

```gdscript
assert(GameState.current_map_id == old_map)
```

应提供：

```gdscript
func assert_game_state_restored(before: Dictionary) -> void:
    var after := Support.snapshot_game_state()
    var differences := Support.compare_variants(before, after, "GameState")
    assert(differences.is_empty(), "STATE_RESTORE_MISMATCH: %s" % differences)
```

`snapshot_game_state()`和`restore_game_state()`必须成对维护。新增了warehouse快照，就必须恢复warehouse；任何被fixture或action修改的字段都必须进入快照。

建议先单独做一次状态隔离负向测试：故意少恢复一个warehouse格子，确认得到`STATE_RESTORE_MISMATCH`，恢复代码后再继续动态矩阵。

### 10.3 dispatcher不要复制既有玩法逻辑

目标不是再写一套action名单，而是让生产点击与测试经过同一个入口。

推荐形态：

```gdscript
func _on_actor_input(action_id: String) -> void:
    var result := _dispatch_world_action(action_id)
    if str(result.get("code", "")) == "UNSUPPORTED_ACTION":
        _set_status("无法识别的交互。")

func _dispatch_world_action(action_id: String) -> Dictionary:
    # 这里只负责路由到现有handler，不复制战斗、挖矿、抽奖等公式。
    # 每个成功分支返回稳定route/code，未知action返回UNSUPPORTED_ACTION。
    return {"route": route, "code": code}
```

如果现有`_on_actor_input()`参数不同，应按现有签名接入，不要为了套示例破坏信号连接。

测试必须调用`_dispatch_world_action()`或触发真实actor input，并同时验证：

- 返回的route/code。
- 对应面板、session、地图或资源状态差。
- unknown action不打开面板、不创建战斗、不移动地图、不改变资源。

`_world_action_route()`可以保留为dispatcher内部纯分类helper，但不能由测试绕开生产dispatcher单独调用后宣称完成。

### 10.4 领地四态按状态机测试，不要只做演员截图

每张领地图按以下流程分别建case：

```text
rank_low
  设置低军衔 -> 调真实报名入口 -> 返回rank_too_low -> 无challenger

rank_ok
  设置合格军衔 -> 查询/打开报名流程 -> available -> 尚无challenger

challenger_active
  调真实_start_territory_challenge(map_id)
  -> pending challenge正确
  -> 临时守卫出现
  -> battle session锁定该守卫

owned
  从真实挑战状态结算胜利
  -> owned_territory == map_id
  -> pending challenge清空
  -> 临时守卫消失
  -> 报名官显示已占领
```

如果某一步现有API名称不同，先用`rg`找到实际入口再调用；不得直接赋最终字段伪装完成状态迁移。

### 10.5 负向测试使用“先证明变异发生，再证明验证器失败”

每项负向统一采用：

```gdscript
var mutation_applied := false
# 找到明确目标并修改
mutation_applied = true
assert(mutation_applied, "NEGATIVE_FIXTURE_NOT_APPLIED")
var errors := run_same_positive_validator(...)
assert(_has_error_code(errors, "EXPECTED_CODE"))
# 恢复
assert(run_same_positive_validator(...).is_empty())
```

严禁：

```gdscript
if found:
    assert(...)
```

必测目标找不到时，本身就是测试失败，不能静默跳过。

装饰metadata负向应选择已知含装饰的palace，先断言节点非null，再移除metadata。scenario负向应调用与正向矩阵完全相同的runner，不能换成更底层、覆盖范围更窄的验证器。

### 10.6 出口验证分为原版证据与运行时一致性

两者不要混为一谈：

- SWF未确认字段继续标记`evidence_gap`。
- Godot当前运行值记录为`runtime_required_level`、`runtime_availability_rule`。
- 测试比较运行时节点metadata与Godot规则，不得据此宣称已经确认SWF原版值。

创建`NativeExitButton`时一次性写全metadata；验证时不仅检查`has_meta()`，还要比较每个值。

### 10.7 gap验证应按字段展开

先将一个对象的未确认字段展开成复合键：

```text
map_id | object_id | field
```

再把结构化gaps展开成相同复合键，做双向集合比较。这样才能证明不是“对象有一条gap，所以所有字段自动算覆盖”。

### 10.8 推荐提交顺序

不要一次重写全部测试。按以下检查点提交，每个检查点附专项PASS和一个对应负向失败：

1. A：独立always helper、scenario分区验证、真实scenario负向。
2. B：完整snapshot/restore、warehouse、deep equality。
3. C：真实dispatcher接入及unknown action。
4. D：六图24个领地状态。
5. E：出口metadata值比较、字段级gap映射。
6. F：所有负向、专项、相邻、50项全量与冒烟。

PM/SE可在任一检查点指出方法错误，避免错误结构扩散到整份测试。
